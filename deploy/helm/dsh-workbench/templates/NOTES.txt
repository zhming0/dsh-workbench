{{- include "dsh-workbench.validate" . }}
The control plane is installed in {{ .Release.Namespace }}. It has no sandbox
pool of its own: sessions can be created and the Web UI works, but the first
tool call needs a runner. Set one up before using it —

  https://github.com/zhming0/dsh-workbench/blob/main/docs/installations.md

For sandboxes in this cluster, that is the sandbox pool; the
agent-sandbox v1.0.2 controllers are not installed by this chart:

  https://github.com/zhming0/dsh-workbench/blob/main/docs/installations-kas.md

The pool reads two fixed names from this release: the `dsh-runner-config`
ConfigMap holding HOST_URL, and the `dsh-registration-token` Secret.

{{- if .Values.provider.sandboxManager }}

This release owns the provider's sandbox-manager settings: they are mounted
read-only at /data/.dsh/cordis.patch.yml, a dsh patch layer that outranks the
seeded profile file. `helm upgrade` changes them, and the pod restarts.

{{- else }}

No sandbox profile is configured. Point the provider at a runner by setting
provider.sandboxManager in your values file and running `helm upgrade`; the
runner setup pages below show the profile to add.

{{- end }}

{{- if .Values.oidc.enabled }}

The oauth2-proxy reads its configuration from the Secret
"{{ .Values.oidc.existingSecret }}" in {{ .Release.Namespace }}. If it does not
exist yet, create it — until then the pod runs but never becomes Ready:

  kubectl -n {{ .Release.Namespace }} create secret generic {{ .Values.oidc.existingSecret }} \
    --from-literal=OAUTH2_PROXY_OIDC_ISSUER_URL=https://your-idp/realm \
    --from-literal=OAUTH2_PROXY_CLIENT_ID=dsh-host \
    --from-literal=OAUTH2_PROXY_CLIENT_SECRET=… \
    --from-literal=OAUTH2_PROXY_COOKIE_SECRET="$(openssl rand -base64 32 | tr -- '+/' '-_')"

{{- if eq .Values.service.type "LoadBalancer" }}
Once the Secret exists and the load balancer's address resolves for
{{ .Values.oidc.hostname }}, open

  https://{{ .Values.oidc.hostname }}/launch-token

and you land signed in.
{{- else }}
The proxy is running at Service/{{ include "dsh-workbench.fullname" . }}
(port {{ .Values.service.port }}) but not exposed. Point an Ingress, a Gateway
API route, or a LoadBalancer Service of your own at it — the pod labels
(app.kubernetes.io/name, app.kubernetes.io/instance) are a stable target —
then open https://{{ .Values.oidc.hostname }}/launch-token. Whatever fronts
dsh must serve https (the proxy's cookie is secure) and pass WebSockets and
large RPC bodies; docs/kubernetes.md has the nginx-ingress values as a
reference.
{{- end }}

{{- else }}

dsh is reachable over a port-forward only. In another terminal:

  kubectl -n {{ .Release.Namespace }} port-forward deploy/{{ include "dsh-workbench.fullname" . }} 3000:3000

Then open http://localhost:3000/launch-token — or take the tokenized URL from
the host log and open it directly:

  kubectl -n {{ .Release.Namespace }} logs deploy/{{ include "dsh-workbench.fullname" . }} | grep 'dsh web:'

{{- end }}

Add provider secrets (a GITHUB_TOKEN is also the Git credential for
github.com) from the Web UI's Settings → Secrets page, once you can reach the
UI.
